# ai-workflow

Окружение для ИИ-агента, которое превращает работу над задачами в повторяемый процесс: единые правила, изолированные git worktree, стенды и учёт.

Репозиторий не содержит код продукта. Это правила, шаблоны, хуки и инфраструктура, по которым агент работает с вашими проектами.

## Зачем это нужно

Агент, который правит код в нескольких репозиториях, без общих правил каждый раз заново выясняет, где лежит код, что можно менять и в какой ветке работать. `ai-workflow` задаёт это заранее и одинаково для всех задач.

| Проблема | Решение |
|---|---|
| Несколько проектов и репозиториев | Пространства: у каждого свои источники кода, права и правила |
| Несколько задач одновременно | Своя задача — свой `git worktree`; основная копия только читается |
| Агент трогает лишнее | Права `write` / `ask` / `read` на каждый источник |
| Секреты попадают в код | Отдельный файл секретов, агент не выводит и не сохраняет значения |
| Стенды занимают порты | nginx-прокси раздаёт любое число стендов под путями `/<имя>/` |
| Непонятно, что сделано | Журнал задачи и файл учёта worktree |

## Как это работает

```
пространство (workspaces/<ws>/ws.yaml)
  └── задача (tasks/<задача>/task.yaml + описание)
        └── worktree репозитория → ветка задачи → коммиты → merge request
```

- **Пространство** — проект с настройками: где лежит код, какие права у источников, какие правила действуют.
- **Задача** — папка с `task.yaml` и файлом описания. Стадия задаёт, что агенту разрешено.
- **Worktree** — отдельная рабочая копия репозитория для задачи. Основная копия остаётся нетронутой.

Правила читаются по цепочке: `AGENTS.md` → `rules/` → правила пространства из `ws.yaml` → правила репозитория. Если правила противоречат друг другу, агент останавливается и спрашивает.

### Стадии задачи

| Стадия | Что делает агент | Коммиты и push |
|---|---|---|
| `research` | Исследует код, пишет документы в папку задачи | Запрещены |
| `plan` | То же плюс план реализации | Запрещены |
| `implement` | Правит код на ветке задачи | По настройкам `task.yaml` |

## Быстрый старт

1. Склонируйте репозиторий в любое место. Корень клона — `$ROOT`.

2. Создайте `env.yaml` по `templates/env.yaml`: временная папка, файл секретов, прокси стендов и пути к коду.

3. Создайте файл секретов по `templates/secrets.yaml` (путь задаётся в `env.yaml` → `secrets_file`).

4. Создайте пространство. В чате с агентом:

   ```
   hook:new-workspace <ws>
   ```

   Затем заполните `workspaces/<ws>/ws.yaml`: источники кода и права `write` / `ask` / `read`, настройки git, правила пространства, ключи секретов, стенды.

5. Проверьте настройки:

   ```bash
   bin/check-config
   ```

6. Создайте задачу:

   ```
   hook:new-task <ws> <задача>
   ```

   Заполните `task.md` и `task.yaml`: стадию, ветки, права на коммит и push.

7. Попросите агента выполнить задачу:

   ```
   workspaces/<ws>/tasks/<задача>
   ```

## Структура

```
AGENTS.md            правила агента
env.yaml             переменные этой машины (не коммитится)
secrets.yaml         секреты (не коммитится)
rules/               общие правила: схемы YAML, worktree, журнал, MR, стенды
templates/           шаблоны env.yaml, secrets.yaml, ws.yaml, task.yaml и др.
hooks/               хуки hook:<имя> и реестр автозапуска TRIGGERS.md
bin/check-config     проверка всех YAML по схемам
registry/            учёт worktree (локальный)
infra/nginx-env/     прокси стендов: nginx + панель + envctl
workspaces/<ws>/
  ws.yaml            настройки пространства
  rules/             правила пространства
  tasks/<задача>/    активные задачи: настройки, описание, журнал, worktree
  _archive/<задача>/ завершённые задачи
```

## Повседневная работа

- Агент создаёт worktree сам, на ветке из `task.yaml` → `git.branch`.
- Каждый шаг записывается в журнал задачи, если `journal: true`.
- Статусы worktree видны в `registry/WORKTREES.md`.
- Хуки запускаются вручную (`hook:<имя>`) или автоматически по событиям из `hooks/TRIGGERS.md`.
- Проверить все настройки можно в любой момент: `bin/check-config [<ws>]`.

## Стенды

Если внешних портов мало, стенды раздаёт nginx из `infra/nginx-env` под путями `/<имя>/`.

- Внешний адрес — `env.yaml` → `proxy.url`.
- Панель со списком стендов — `$PROXY_URL/_env/`.
- Стенд поднимается на порту из `envctl free-port` и сразу регистрируется через `envctl add`.

Подробно — `infra/nginx-env/README.md` и `rules/stands-proxy.md`.

## Требования

- Python 3 и PyYAML — для `bin/check-config` и `envctl`.
- Git — для worktree и задач.
- nginx скачивается автоматически при первом `envctl up`; устанавливать его в систему не нужно.

## Ограничения

- Репозиторий не управляет вашим кодом: он задаёт процесс работы агента с ним.
- Секреты и настройки машины (`env.yaml`, `secrets.yaml`, `workspaces/*`) не коммитятся.
- Автоматический запуск хуков включается только строками в `hooks/TRIGGERS.md`.

## Сводка

`ai-workflow` — окружение для ИИ-агента, работающего с задачами в нескольких проектах. Пространство задаёт источники кода, права и правила; задача задаёт стадию и ветку; каждая задача идёт в отдельном git worktree, а основная копия только читается. Настройки хранятся в строгих YAML-файлах и проверяются `bin/check-config`, секреты лежат отдельно, стенды раздаёт nginx-прокси. Начните с `env.yaml`, затем `hook:new-workspace`, `hook:new-task` и попросите агента выполнить задачу.
