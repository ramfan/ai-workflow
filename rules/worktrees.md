# Расширение: параллельная работа через git worktree

Это расширение правил из `AGENTS.md` (раздел 6). Оно обязательно так же, как основной документ.

Над одним репозиторием одновременно могут работать несколько агентов. Чтобы они не мешали друг другу, **каждая задача работает в своём git worktree**. Основная копия репозитория принадлежит пользователю.

Это расширение:
- **добавляет исключения** к п. 1.1 `AGENTS.md`: разрешает правки в worktree задачи и в файле `registry/WORKTREES.md`;
- **заменяет** в п. 2.6 `AGENTS.md` способ перехода на ветку: вместо переключения ветки в основной копии создаётся worktree.

Все остальные правила `AGENTS.md` действуют без изменений.

---

## 1. Термины

| Термин | Что это |
|---|---|
| **Источник** | Элемент `ws.yaml` → `sources`. |
| **Репозиторий** | Папка с собственным `.git`. Для источника `kind: repo` — сам `path`. Для `kind: repos-dir` — каждый репозиторий внутри `path` на любой глубине; папка `path` и промежуточные папки репозиториями не являются. |
| **Путь репозитория** | Для `repo` — имя папки `path`. Для `repos-dir` — путь репозитория относительно `path`, например `project/backend`. |
| **Основная копия** | Репозиторий в источнике. В ней не работают. |
| **Папка задачи** | `$TASK` = `$ROOT/workspaces/<ws>/tasks/<задача>/`. |
| **Worktree задачи** | Рабочая копия репозитория для задачи: `$TASK/<путь-репозитория>/`. Например `$TASK/project/` или `$TASK/project/backend/service_logging`. Если в пространстве несколько источников, можно добавить папку источника, чтобы пути не пересекались. |
| **Файл учёта** | `$ROOT/registry/WORKTREES.md`. |
| **Настройки** | `ws.yaml` → `git` и `task.yaml` → `git` (`rules/config.md`). |

---

## 2. Что можно и что нельзя

### 2.1. Основная копия

- **СТРОГО ЗАПРЕЩАЕТСЯ** править файлы, переключать ветки, делать `commit`, `stash`, `reset`, `checkout`, `pull`, ставить зависимости и выполнять любые другие изменяющие действия в основной копии. Это не зависит от `access` источника.
- Разрешены только: чтение, `git fetch`, команды `git worktree add / lock / unlock / remove / prune / list`.

### 2.2. Worktree задачи

- Все правки по задаче вносятся **только** в worktree этой задачи.
- Worktree создаётся только для репозиториев из источников с `access: write`, либо `access: ask` после явного разрешения пользователя. Для `access: read` worktree создаётся только в стадиях `research` / `plan` или для чтения, сборки и тестов — без ветки.
- **СТРОГО ЗАПРЕЩАЕТСЯ** трогать worktree других задач: править, коммитить, удалять, снимать блокировку.

### 2.3. Файл учёта

- Агент правит **только строки своей задачи**, точечной заменой (инструмент Edit). Чужие строки не трогает, файл целиком не перезаписывает.
- Файл учёта — это **не задача**.

## 3. Настройки

Перед работой прочитай `ws.yaml` → `git` и `task.yaml` → `git`.

### 3.1. Стадия (`task.yaml` → `stage`)

| Стадия | Что делать |
|---|---|
| `research`, `plan` | **Всегда** создавай worktree **без ветки** (`--detach`) — только для чтения (п. 3.6). |
| `implement` | Работай в worktree на ветке `git.branch` по этому документу. |

Основную копию для работы над задачей не используй ни в какой стадии: она может стоять на другой ветке.

### 3.2. Обязательные поля

Все поля `task.yaml` → `git` обязательны по схеме. Дополнительно для `implement`: `branch` не `null`. Если поле не заполнено или осталась заглушка — **СТРОГО ЗАПРЕЩАЕТСЯ** продолжать. Остановись и спроси пользователя.

### 3.3. Одна ветка на всю задачу

- Имя из `git.branch` используется **везде**: в каждом репозитории задачи, в корне и во всех подмодулях.
- Если ветки ещё нет ни локально, ни на сервере (`origin`), она создаётся от `git.base_branch`.

### 3.4. Репозитории и подмодули — по необходимости

- Список репозиториев (`repos-dir`) и подмодулей в задаче **не задаётся**. Агент сам определяет, что нужно править.
- Перед первой правкой в новом репозитории или подмодуле:
  1. переведи его на ветку задачи (раздел 4);
  2. добавь его в учёт;
  3. сообщи пользователю, что начинаешь править этот репозиторий или подмодуль.
- Не правь репозитории и подмодули, которые не нужны для задачи.

### 3.5. Корневой репозиторий с подмодулями

Действует при `ws.yaml` → `git.submodules: true`. Значение `root_branch` — из `task.yaml`, а если там `null` — из `ws.yaml`.

| `root_branch` | Что делать |
|---|---|
| `true` | Worktree создаётся на ветке задачи. Правки и коммиты в корне — в ней. |
| `false` | Worktree создаётся от базовой ветки без ветки (`--detach`). В корне **ничего не коммить** — правки только в подмодулях. Если без правок в корне не обойтись — спроси пользователя. |

### 3.6. Стадии `research` и `plan`

- **Какую ветку исследовать:** `git.branch`, если заполнена. Иначе — `git.base_branch`.
- Worktree создаётся **всегда**, без ветки: `--detach origin/<ветка-исследования>` (раздел 4, шаг 3).
- В таком worktree **СТРОГО ЗАПРЕЩАЕТСЯ** коммитить и отправлять что-либо. Создавать ветки — тоже. Он только для чтения, сборки и тестов.
- Подмодули (`submodules: true`) скачивай всегда (шаг 4), но на ветки их не переводи. Зависимости (шаг 5) — только если нужна сборка или тесты.
- `repos-dir`: worktree создаётся для каждого репозитория, который понадобилось исследовать.
- Если по итогам нужны правки — сообщи пользователю. Стадию меняет только пользователь в `task.yaml`.

### 3.7. Коммиты и push

| Поле | Значение | Что делать |
|---|---|---|
| `commit` | `true` | Коммить сам. |
| `commit` | `ask` | Перед каждым коммитом покажи изменения и спроси пользователя. |
| `commit` | `false` | Не коммить. |
| `push` | `true` | Отправляй сам. |
| `push` | `ask` | Перед каждой отправкой спроси пользователя. |
| `push` | `false` | Не отправляй. |

- Если `ws.yaml` → `git.jira_in_commit: true`, в сообщении каждого коммита указывай `task.yaml` → `jira`. Если `jira: null` — спроси пользователя. Git-хуки основной копии в подмодулях worktree могут не работать — пиши ключ вручную.
- Порядок с подмодулями: сначала коммит и push в подмодуле, потом обновление указателя подмодуля в корне. Указатель в корне обновляй, только если `root_branch: true`.
- Оформление MR — по `rules/merge-requests.md`.

## 4. Создание worktree

Выполняй по шагам. При любой ошибке остановись, поставь в учёте статус `ждёт ответа` и сообщи пользователю.

### Шаг 1. Проверка

- Посмотри `git worktree list` в основной копии и строки своей задачи в файле учёта.
- Если worktree этой задачи уже есть (задачу продолжает новая сессия) — **не создавай новый**. Работай в существующем, обнови в учёте сессию и время.
- Если ветка задачи уже открыта в другом worktree или в основной копии (`already checked out`) — **остановись и спроси пользователя**.

### Шаг 2. Запись в учёт

Добавь строку со статусом `создаётся` (раздел 6). Если файла нет — создай его по шаблону.

### Шаг 3. Создание

В основной копии:

```bash
git fetch origin
R="<ws>/<задача>, <ID сессии>"

# ветка задачи уже есть локально или на сервере:
git worktree add --lock --reason "$R" <путь-worktree> <ветка>

# ветки нет — создать от базовой без привязки к ней:
git worktree add --lock --reason "$R" --no-track -b <ветка> <путь-worktree> origin/<базовая-ветка>

# root_branch: false:
git worktree add --lock --reason "$R" --detach <путь-worktree> origin/<базовая-ветка>

# стадия research / plan:
git worktree add --lock --reason "$R" --detach <путь-worktree> origin/<ветка-исследования>
```

`--no-track` обязателен: иначе новая ветка привяжется к базовой, `git push` упадёт, а проверки перед удалением дадут неверный результат.

Для `repos-dir` этот шаг выполняется отдельно для каждого репозитория, когда он понадобился (п. 3.4).

### Шаг 4. Подмодули (`submodules: true`)

Подмодули в новом worktree **пустые**. Скачай их (данные скачиваются заново, это долго):

```bash
cd <путь-worktree>
git submodule update --init --recursive
```

Подмодули после этого не на ветке (detached HEAD). В `research` / `plan` так и оставь. В `implement` переводи на ветку задачи **только те**, которые понадобилось править (п. 3.4):

```bash
cd <путь-worktree>/<путь-подмодуля>
git fetch origin
git switch <ветка>                                            # если ветка уже есть
git switch --no-track -c <ветка> origin/<базовая-ветка>       # если ветки нет
```

### Шаг 5. Зависимости

Как ставить зависимости (команда, особенности), описывают правила пространства. Общие требования:

- Зависимости ставятся заново в worktree. Не копируй и не связывай ссылками папки зависимостей из основной копии.
- В `research` / `plan` — только если нужна сборка или тесты.

### Шаг 6. Готово

Поставь в учёте статус `в работе` и сообщи пользователю путь к worktree. Наступает событие `worktree-created` (`AGENTS.md`, п. 8.2).

---

## 5. Работа в worktree

- Все команды (сборка, тесты, линтер, git) запускай **из worktree задачи**.
- Первая отправка новой ветки: `git push -u origin <ветка>`.
- Если процесс другой задачи занимает порт — не останавливай чужой процесс. Запусти на другом порту или спроси пользователя.

## 6. Файл учёта `registry/WORKTREES.md`

### 6.1. Шаблон

```markdown
# Учёт worktree

Файл ведут агенты. Каждый агент правит только строки своей задачи.
Правила: rules/worktrees.md

| Пространство | Задача | Репозиторий | Путь worktree | Ветка | Подмодули | Сессия | Статус | Начато | Обновлено | Комментарий |
|---|---|---|---|---|---|---|---|---|---|---|
```

### 6.2. Строки

- Одна строка на **каждый репозиторий** задачи. У задачи, затронувшей три репозитория из `repos-dir`, — три строки.
- «Пространство» — `ws.yaml` → `name`. «Задача» — имя папки задачи.
- «Репозиторий» — путь репозитория (раздел 1).
- «Путь worktree» — от `$ROOT`, например `workspaces/project-frontend/tasks/TASK-123/charts`.
- «Ветка» — имя ветки задачи; при `root_branch: false` — `— (detached)`; для `research` / `plan` — `<ветка> (detached, только чтение)`.
- «Подмодули» — список подмодулей, переведённых на ветку задачи, через запятую. Если подмодулей нет — `—`.
- «Сессия» — ID текущей сессии агента.
- Время — в формате `date '+%Y-%m-%d %H:%M %z'`.

### 6.3. Статусы

| Статус | Когда |
|---|---|
| `создаётся` | Создание worktree, скачивание подмодулей, установка зависимостей |
| `в работе` | Агент работает |
| `ждёт ответа` | Агент задал вопрос пользователю |
| `готово, ждёт закрытия` | Работа сделана, ждём, когда пользователь закроет задачу |
| `удаляется` | Пользователь закрыл задачу, worktree удаляется |

### 6.4. Когда обновлять

- при смене статуса или сессии;
- при переводе нового репозитория или подмодуля на ветку задачи;
- в конце **каждого** ответа пользователю — колонки «Обновлено» и «Комментарий».

По давно не обновлявшейся строке пользователь видит, что агент, скорее всего, завис.

## 7. Удаление worktree

Worktree удаляется **только после того, как пользователь явно сказал, что задача закрыта**. До этого статус — `готово, ждёт закрытия`.

### Шаг 1. Проверки

Поставь статус `удаляется`. В каждом worktree задачи:

```bash
cd <путь-worktree>
git status --short
git log --oneline HEAD --not --remotes
git submodule foreach --recursive 'git status --short; git log --oneline HEAD --not --remotes'
```

Если хоть где-то есть незакоммиченные изменения или коммиты, которых нет на сервере, — **остановись и спроси пользователя**. Так же поступай при `push: false`: неотправленные коммиты при удалении **пропадут безвозвратно**.

### Шаг 2. Удаление

Только если проверки чистые или пользователь явно разрешил, в основной копии:

```bash
git worktree unlock <путь-worktree>
git worktree remove --force <путь-worktree>
git worktree prune
```

`--force` обязателен: без него git не удаляет worktree с подмодулями.

### Шаг 3. Учёт

- Удали строки своей задачи из файла учёта.
- Проверь, что worktree нет в `git worktree list`.
- Папку задачи, `task.yaml`, описание и `journal/` **не удаляй**. Переносить её в `_archive/` — только по просьбе пользователя (`AGENTS.md`, п. 2.7).
- Сообщи пользователю, что worktree удалены.

## 7а. Перенос папки задачи с worktree (например, в архив)

Только по прямой просьбе пользователя (`AGENTS.md`, п. 2.7).

- `git worktree move` **не переносит** worktree с подмодулями. Простой `mv` ломает связи: git хранит абсолютные и относительные пути в обе стороны.
- Порядок:
  1. Проверки из раздела 7, шаг 1 (без смены статуса). Убедись, что в папке задачи никто не работает: нет запущенных сессий агентов, сборок, dev-серверов.
  2. Сделай резервную копию метаданных: `tar -czf $TMP/<имя>.tgz -C <основная копия>/.git --exclude=objects worktrees`.
  3. Перенеси папку задачи целиком (`mv`).
  4. Почини пути:
     - в каждом файле `.git` внутри worktree (корень и подмодули) — `gitdir:`; относительный путь пересчитай от нового места, абсолютный оставь;
     - в основной копии `.git/worktrees/<имя>/gitdir` — новый абсолютный путь к `<worktree>/.git`;
     - `core.worktree` в `.git/worktrees/<имя>/modules/**/config` — новый путь к подмодулю, в том же виде (относительный или абсолютный).
  5. Проверь: `git worktree list` показывает новые пути, `git worktree prune -n -v` ничего не предлагает удалить, `git status` и `git submodule foreach --recursive git status --short` в worktree работают и не показывают новых изменений.
  6. Обнови пути в строках задачи в файле учёта.
- Если любая проверка не прошла — восстанови метаданные из копии, верни папку на место и спроси пользователя.

---

## 8. Проверка учёта по просьбе пользователя

1. Сравни файл учёта с `git worktree list` в каждом репозитории, по которому есть строки в учёте:
   - worktree есть в git, но нет в файле — «потерянный»;
   - строка есть в файле, но worktree нет в git — «осиротевшая».
2. Отметь строки, у которых «Обновлено» давно не менялось.
3. Покажи результат. **Ничего не исправляй и не удаляй** без прямого указания.

## 9. Краткая памятка

| Действие | Разрешено? |
|---|---|
| Правки, коммиты, смена ветки в основной копии | Нет |
| `git fetch` и `git worktree …` в основной копии | Да |
| Работать над задачей в основной копии (в любой стадии) | Нет |
| Worktree в стадии `research` / `plan` | Да, всегда без ветки (`--detach`) |
| Коммиты, push, создание веток в `research` / `plan` | Нет |
| Worktree на ветке для источника `access: ask` без разрешения | Нет |
| Создавать worktree при незаполненных настройках задачи | Нет, спроси пользователя |
| Правки в worktree своей задачи | Да |
| Правки в чужом worktree | Нет |
| Ветка с именем, отличным от `git.branch` | Нет |
| Новый репозиторий или подмодуль, нужный для задачи | Да, с записью в учёт и сообщением пользователю |
| Коммит в корне при `root_branch: false` | Нет |
| Править свои строки в `registry/WORKTREES.md` | Да, точечно |
| Править чужие строки или перезаписывать файл учёта | Нет |
| Удалить worktree до закрытия задачи пользователем | Нет |
| Удалить worktree с неотправленными изменениями | Нет, спроси пользователя |

## Сводка

Каждая задача работает в своём git worktree внутри папки задачи; основная копия только читается. Какие репозитории брать и с какими правами — из `ws.yaml` → `sources`; ветка, базовая ветка, права на коммит и push — из `task.yaml` → `git`. В `research` / `plan` worktree всегда без ветки и только для чтения. Каждый worktree учитывается строкой в `registry/WORKTREES.md`; агент правит только свои строки. Удаление — только после закрытия задачи пользователем и после проверки, что всё отправлено.
