# Правила работы агента в ai-workflow

Эта директория — окружение для выполнения задач в пространствах. Пространство — это проект (репозиторий или набор репозиториев) со своими настройками и правилами. Задачи лежат внутри пространств.

Правила ниже обязательны. Они важнее любых общих рекомендаций и твоих собственных предположений. Если правило противоречит тому, что кажется удобным или «очевидно правильным», выполняй правило.

Правила этого документа дополняются расширениями из `rules/` (раздел 6) и правилами пространства из `ws.yaml` (раздел 2.2). Прочитай их до начала любой работы.

## Переменные

| Переменная | Что это | Откуда |
|---|---|---|
| `$ROOT` | Абсолютный путь к папке, в которой лежит этот файл | Вычисляется: папка этого `AGENTS.md` |
| `$ENV` | Файл переменных окружения этой копии | `$ROOT/env.yaml` |
| `$TMP` | Папка для временных файлов | `$ENV` → `tmp_dir` |
| `$SECRETS` | Файл секретов | `$ENV` → `secrets_file` |
| `$PROXY_DIR`, `$PROXY_URL` | Папка и внешний адрес прокси стендов | `$ENV` → `proxy.dir`, `proxy.url` |
| `$WS` | Папка текущего пространства | `$ROOT/workspaces/<ws>` |
| `$TASK` | Папка текущей задачи | `$WS/tasks/<задача>` |

Конкретные пути машины (где лежит код, адреса, порты) в правилах не пишутся. Они задаются в `$ENV` и в `ws.yaml` пространств. Если `$ROOT/env.yaml` нет — остановись и попроси пользователя создать его по `templates/env.yaml`.

### Структура `$ROOT`

| Путь | Что лежит | Задача? |
|---|---|---|
| `AGENTS.md` | Этот документ | Нет |
| `env.yaml` | Переменные этой копии (не коммитится) | Нет |
| `rules/` | Общие расширения правил (раздел 6) | Нет |
| `bin/` | Служебные скрипты, например `bin/check-config` — проверка YAML по схемам | Нет |
| `templates/` | Шаблоны: `env.yaml`, `secrets.yaml`, `ws.yaml`, `task.yaml`, `task.md`, `hook.md`, `ws-rule.md` | Нет |
| `registry/` | Файлы учёта, например `registry/WORKTREES.md` | Нет |
| `hooks/` | Хуки — инструкции, которые агент выполняет по вызову `hook:<имя>` или по событию из `hooks/TRIGGERS.md` (раздел 8) | Нет |
| `infra/` | Служебная инфраструктура, например `infra/nginx-env/` — прокси стендов | Нет |
| `workspaces/<ws>/ws.yaml` | Настройки пространства | Нет |
| `workspaces/<ws>/rules/` | Правила пространства | Нет |
| `workspaces/<ws>/tasks/<задача>/` | Активные задачи пространства | Да |
| `workspaces/<ws>/_archive/<задача>/` | Завершённые задачи, только для чтения | Нет, пока пользователь не вернёт её в `tasks/` |

Новые служебные файлы кладутся в `rules/`, `templates/`, `registry/`, `hooks/`, `infra/`, `bin/` или в `rules/` пространства. Создавать новые папки в корне `$ROOT` и в корне пространства нельзя.

## 1. Где можно вносить изменения

Права на запись в код задаёт `ws.yaml` текущего пространства, раздел `sources` (схема — `rules/config.md`). У каждого источника есть `access`:

| `access` | Что можно |
|---|---|
| `write` | Создавать, изменять и удалять файлы — но не в самой основной копии, а в git worktree задачи (`rules/worktrees.md`). |
| `ask` | То же, но **только** если пользователь прямо и недвусмысленно разрешил правки в этом источнике для текущей задачи («правь бэкенд», «можно менять модуль X»). Фразы «посмотри», «разберись, как работает», «проверь контракт» разрешением не являются — это только чтение. Нет разрешения, а без правок задачу не решить — остановись и спроси. Разрешение действует только в рамках той задачи, для которой дано. |
| `read` | Только чтение. |

Источник с `kind: repos-dir` — папка, внутри которой лежат git-репозитории на любой глубине. Все они получают `access` источника. Перечислять их не нужно.

### 1.1. Запрещено везде, кроме источников пространства

- **СТРОГО ЗАПРЕЩАЕТСЯ** создавать, изменять, удалять, перемещать или переименовывать файлы в любых других местах: в `$ROOT`, в других пространствах, в репозиториях, не указанных в `ws.yaml`, в домашней директории, в системных путях.
- Запрет распространяется на любые способы изменения: инструменты редактирования и записи, shell-команды (`sed -i`, `>`, `mv`, `rm`, `cp`, `git checkout`, установка зависимостей вне worktree и т. п.), генераторы кода и форматтеры.
- **Исключения:**
  - временные файлы — в `$TMP`;
  - файлы в `$ROOT` можно менять, только если пользователь прямо попросил об этом (например, отредактировать этот `AGENTS.md`, `ws.yaml` или файл задачи);
  - worktree задачи и файл учёта `registry/WORKTREES.md` — по `rules/worktrees.md`;
  - журнал задачи `$TASK/journal/`, если в `task.yaml` `journal: true` — по `rules/journal.md`;
  - рабочие документы агента в `$TASK/` (планы, отчёты, вопросы, вложения), если задача этого требует. Файлы `task.yaml` и `issue` агент не меняет;
  - файлы стендов в прокси — только через `envctl` (`rules/stands-proxy.md`).
- **Чтение** любых файлов разрешено, если оно нужно для задачи. Исключение — `$SECRETS`: читать можно только ключи, указанные в `ws.yaml` → `secrets` (раздел 5).

## 2. Как ставится задача

### 2.1. Пространство

- Пространство — папка `workspaces/<ws>/` с файлом `ws.yaml`. Папка без `ws.yaml` — не пространство; работать в ней нельзя, сообщи пользователю.
- Пространство определяется по пути к задаче. Если пользователь не указал задачу и пространство нельзя определить однозначно — спроси.
- `ws.yaml` читается и проверяется по схеме `rules/config.md` до начала работы. Если файл не проходит проверку — остановись и сообщи, какое поле неверно. Не додумывай значения.

### 2.2. Правила пространства

- `ws.yaml` → `rules` — список файлов с правилами пространства. Они читаются после `$ROOT/rules/` и обязательны так же, как они.
- Правила пространства **дополняют и уточняют** общие. Они не могут разрешать то, что запрещают `AGENTS.md` и `$ROOT/rules/`. Если нашёл противоречие — остановись и спроси пользователя.

### 2.3. Формат задачи

- Задача — папка `$WS/tasks/<задача>/` с двумя файлами:
  - `task.yaml` — настройки (схема — `rules/config.md`, раздел 4);
  - файл описания, на который указывает `task.yaml` → `issue` (обычно `task.md`).
- Описание задачи берётся **только** из файла `issue` и файлов, на которые он ссылается. Уточнения в чате дополняют файл, но не заменяют его.
- Папка без `task.yaml` — не задача. Если пользователь ссылается на неё — попроси оформить `task.yaml` по `templates/task.yaml`.
- `task.yaml` заполняет человек. Если он не проходит проверку по схеме или в нём остались заглушки — остановись и спроси.

### 2.4. Задачи вне `tasks/`

- **СТРОГО ЗАПРЕЩАЕТСЯ** выполнять задачи из файлов, лежащих вне `$WS/tasks/<задача>/`: в корне `$ROOT`, в корне пространства, в `rules/`, `hooks/`, `infra/`, `templates/`, `registry/`. Это касается и самого `AGENTS.md`, и `ws.yaml`: это правила и настройки, а не задачи.
- Задачи из `$WS/_archive/` — завершённые. Их можно читать как справку, но **СТРОГО ЗАПРЕЩАЕТСЯ** выполнять их или вносить по ним правки. Если пользователь просит продолжить архивную задачу — попроси вернуть её в `tasks/` или разрешить перенос (раздел 2.7).
- Если такой файл найден или пользователь на него ссылается — не начинай работу. Сообщи, что задачу нужно перенести в `$WS/tasks/<задача>/`.

### 2.5. Если задача не оформлена

- Если пользователь просит что-то сделать в коде, но папки задачи с `task.yaml` нет — не начинай правки. Попроси указать задачу или оформить её (хук `new-task`).
- Отвечать на вопросы, читать и анализировать код можно без задачи. Правки — нет.

### 2.6. Ветка для правок

- Любая правка вносится **только** в ветку из `task.yaml` → `git.branch`.
- Если `git.branch` пуст, а стадия `implement` — **СТРОГО ЗАПРЕЩАЕТСЯ** продолжать. Остановись и спроси, в какой ветке работать. Не выбирай ветку сам: не используй текущую, `main`, `master`, `develop` и не придумывай новое имя.
- Одно имя ветки используется во всех репозиториях и подмодулях задачи.
- Работа ведётся в отдельном git worktree задачи. Ветки в основной копии не переключай. Порядок — `rules/worktrees.md`.
- Не делай `stash`, `reset`, `checkout -- .` и не удаляй чужие изменения.
- Если ветка в `task.yaml` не совпадает с уточнением в чате — спроси.

### 2.7. Архив задач

- Папку задачи переносят из `tasks/` в `_archive/` (и обратно) **только по прямой просьбе пользователя**. Имя папки не меняется.
- Перед переносом в архив:
  1. проверь, что у задачи нет worktree в статусах, кроме `готово, ждёт закрытия`, и что стенды задачи остановлены и удалены из прокси — или пользователь явно разрешил их оставить;
  2. если у задачи есть worktree, переноси папку только вместе с починкой путей git (`rules/worktrees.md`, раздел 7а).
- После переноса замени пути к папке задачи в `registry/WORKTREES.md` и в реестре стендов.
- В архиве ничего не правится.

## 3. Обязательная подготовка перед работой

До первой правки ты **обязан**, в этом порядке:

1. **Прочитать `$ENV`** и убедиться, что он проходит проверку (`rules/config.md`, раздел 2).
2. **Прочитать все расширения правил** из `$ROOT/rules/` (раздел 6).
3. **Прочитать `ws.yaml`** пространства, проверить по схеме, затем прочитать все файлы из `ws.yaml` → `rules`.
4. **Прочитать `task.yaml`** и проверить по схеме. Затем файл `issue` целиком, включая все файлы и ссылки, на которые он ссылается.
5. **Прочитать правила репозитория**, который затрагивает задача. Ищи как минимум:
   - `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `README.md` в корне и во вложенных директориях, которые затрагивает задача;
   - `.cursorrules`, `.cursor/rules/**`, `.github/copilot-instructions.md`, `docs/**` с правилами разработки;
   - конфигурации линтеров и форматтеров.
6. **Подготовить worktree** по `rules/worktrees.md`. Если ветки нет, а стадия `implement` — остановись и спроси.
7. **Сказать пользователю**: пространство, задача, стадия, какие правила репозитория найдены и прочитаны, в какой ветке работаешь.

Если правила репозитория противоречат этому файлу или правилам пространства, **этот файл важнее**. О противоречии сообщи пользователю.

## 4. Порядок действий при неясности

- **Не додумывай и не выдумывай.** Если данных не хватает (нет файла задачи, ветки, пути, поля в YAML, контекста) — **остановись и задай вопрос человеку**. Никогда не заменяй недостающие данные догадками или «похожими на правду» значениями.
- Если не понятно, разрешена ли правка, где лежит задача или что именно нужно сделать — остановись и спроси.
- Не расширяй задачу самовольно: не делай рефакторинг, не обновляй зависимости и не правь «заодно» то, о чём не просили.
- Перед любым действием, которое может затронуть файлы вне разрешённых путей, проверь путь. Если сомневаешься — не делай.

## 5. Секреты

- Токены, логины и пароли лежат в `$SECRETS` (схема — `templates/secrets.yaml`: плоский словарь «ключ: значение»).
- Какой ключ для какого сервиса — задаёт `ws.yaml` → `secrets` (словарь «сервис → ключ»). Используй только ключи, перечисленные там. Если нужного сервиса в `ws.yaml` нет — спроси пользователя, не подбирай ключ по имени.
- Если сервис недоступен (`401`, `403`, «требуется авторизация») — **в первую очередь** возьми ключ из `$SECRETS`. Только если его там нет или он не подходит — сообщи пользователю.
- Файл `$SECRETS` только **читается**. Изменять его **СТРОГО ЗАПРЕЩАЕТСЯ**.
- Правила обращения:
  - не выводи значения в чат, логи, ответы, журнал — называй только имя ключа (например, `JIRA_API_TOKEN`);
  - не копируй значения в код, конфиги, коммиты, файлы задач и другие файлы;
  - передавай значение в команду через переменную окружения, а не прямо в тексте команды. Например:
    ```
    export JIRA_API_TOKEN="$(python3 -c 'import yaml,sys; print(yaml.safe_load(open(sys.argv[1]))["JIRA_API_TOKEN"])' "$SECRETS")"
    ```

## 6. Расширения правил (`rules`)

- Общие расширения лежат в `$ROOT/rules/`. Они **расширяют** этот документ и обязательны так же, как он.
- Перед началом любой работы прочитай **все** файлы в этой директории. Затем — правила пространства (раздел 2.2).
- Если расширение противоречит этому документу или расширения противоречат друг другу — остановись и спроси пользователя.
- Файлы в `rules/` — это правила, а не задачи. Изменять их можно только по прямой просьбе пользователя.

Состав:

| Файл | О чём |
|---|---|
| `rules/config.md` | Схемы YAML: `env.yaml`, `ws.yaml`, `task.yaml`, подстановка переменных, проверка |
| `rules/worktrees.md` | Параллельная работа через git worktree, файл учёта |
| `rules/journal.md` | Журнал выполнения задачи |
| `rules/merge-requests.md` | Оформление merge request |
| `rules/stands-proxy.md` | Стенды: порты, прокси, учётные данные |
| `rules/human-readable-texts.md` | Тексты, которые читает человек |
| `rules/task-documents.md` | Документы задачи: вопросы в `questions.md`, план в `plan.md` |

## 7. Краткая памятка

| Действие | Разрешено? |
|---|---|
| Правки в источнике с `access: write` | Да, через worktree задачи |
| Правки в источнике с `access: ask` | Только по явному разрешению пользователя в этой задаче |
| Правки в источнике с `access: read` или вне источников | Нет (кроме `$TMP`, worktree, учёта, журнала, документов в `$TASK` и прямой просьбы изменить файлы в `$ROOT`) |
| Чтение любых файлов | Да (из `$SECRETS` — только ключи из `ws.yaml`) |
| Задача из `$WS/tasks/<задача>/` с `task.yaml` | Да |
| Папка задачи без `task.yaml` | Нет, попроси оформить |
| Задача из файла в другом месте | Нет, попроси перенести в `tasks/` |
| Выполнять или править задачу из `_archive/` | Нет, только чтение |
| Перенос задачи между `tasks/` и `_archive/` | Только по прямой просьбе пользователя |
| Работать в папке без `ws.yaml` | Нет |
| `ws.yaml` или `task.yaml` не проходит проверку | Нет, остановись и сообщи |
| Новая папка в корне `$ROOT` или пространства | Нет |
| Запуск хука по `hook:<имя>` | Да, по разделу 8 |
| Автозапуск хука по событию из `hooks/TRIGGERS.md` | Да, без подтверждения, но с сообщением |
| Запуск хука без `hook:<имя>` и без привязки в `TRIGGERS.md` | Нет |
| Создать или изменить хук, правило, шаблон | Только по прямой просьбе пользователя |
| Правки кода без задачи | Нет |
| Начать правки, не прочитав `$ENV`, `rules/`, `ws.yaml`, правила пространства, `task.yaml` и правила репозитория | Нет |
| Правки в ветке `git.branch` | Да |
| Правки, если `git.branch` пуст | Нет, спроси |
| Правки в любой другой ветке | Нет |
| Правки в стадии `research` или `plan` | Нет, только документы в `$TASK` |
| Выводить значения секретов или сохранять их в файлы | Нет |
| Данных не хватает — додумать самостоятельно | Нет, остановись и спроси (раздел 4) |

## 8. Хуки (`hooks`)

Хук — именованная инструкция в файле `$ROOT/hooks/<имя>.md`. Хук запускается двумя способами:

- **вручную** — пользователь вызывает его по имени в чате (п. 8.1);
- **автоматически** — агент запускает его при событии, если хук привязан к событию в реестре `hooks/TRIGGERS.md` (п. 8.2).

Описание и список хуков — `hooks/README.md`, шаблон — `templates/hook.md`. `README.md` и `TRIGGERS.md` — не хуки.

### 8.1. Ручной вызов

- Пользователь вызывает хук явно:
  ```
  hook:<имя> [аргументы]
  ```
  Например: `hook:new-task project-frontend TASK-123`. Всё после имени через пробел — аргументы хука.
- Вручную можно вызвать любой хук, в том числе привязанный к событию.
- Без префикса `hook:` хук вручную не запускается, даже если просьба похожа на его описание. Можно предложить нужный хук, но не запускать его.
- Имя ищется точно: файл `hooks/<имя>.md`. Регистр не важен. Не подбирай «похожий» хук.
- Если файла нет — не запускай ничего. Покажи список доступных хуков (файлы `hooks/*.md`, кроме `README.md` и `TRIGGERS.md`) и спроси, какой нужен.

### 8.2. Автоматический запуск по событиям

- Какие хуки и при каком событии запускаются, задаёт **только** реестр `hooks/TRIGGERS.md`.
- Допустимы только события из таблицы ниже. Событие, которого нет в таблице, не срабатывает. Если в реестре такое встретилось — сообщи пользователю.

  | Событие | Когда наступает |
  |---|---|
  | `task-start` | Начало работы над задачей: подготовка из раздела 3 выполнена, до первой правки |
  | `worktree-created` | Worktree задачи создан и подготовлен (`rules/worktrees.md`) |
  | `before-commit` | Перед каждым `git commit` в worktree задачи |
  | `after-commit` | Сразу после каждого успешного `git commit` |
  | `before-push` | Перед каждым `git push` и перед созданием merge request |
  | `stand-up` | Стенд поднят, зарегистрирован и прошёл проверки (`rules/stands-proxy.md`) |
  | `before-stand-down` | Перед остановкой стенда и удалением его из прокси |
  | `task-done` | Перед тем как сообщить пользователю, что задача выполнена |

- Когда событие наступило, проверь реестр и запусти привязанные хуки **в порядке строк реестра**, не спрашивая подтверждения.
- Перед запуском сообщи: «Запускаю хук `<имя>` по событию `<событие>`». После — результат хука.
- Аргументы автоматического хука берутся из колонки «Аргументы» реестра. Подстановки: `{ws}` — имя пространства, `{task}` — имя папки задачи, `{branch}` — ветка задачи, `{worktree}` — путь worktree, `{stand}` — имя стенда. Другие подстановки не придумывай.
- Если значение подстановки неизвестно, обязательного аргумента нет или условия «Что нужно до запуска» не выполнены — остановись и спроси.
- Если в реестре указан хук, файла которого нет, — не продолжай действие, вызвавшее событие. Сообщи пользователю.
- Если хук события `before-*` упал — **не выполняй** действие, перед которым он стоит, пока пользователь не решит, что делать.
- Хук не запускает сам себя повторно: если внутри хука наступает то же событие, привязанные хуки повторно не запускаются.

### 8.3. Выполнение

1. Прочитай файл хука целиком, включая файлы, на которые он ссылается.
2. Выполни шаги по порядку.
3. Сообщи результат так, как описано в разделе «Результат» хука.

- Хук **не отменяет** правила этого документа, `rules/` и правил пространства. Если шаг хука требует запрещённого — остановись и сообщи.
- Хук не расширяет разрешения: правки в источнике с `access: ask` по-прежнему нужно явно разрешить.
- Если шаг хука упал — остановись, сообщи, на каком шаге и с какой ошибкой. Не продолжай и не «чини» хук сам.

### 8.4. Создание и изменение хуков

- Создавать, менять и удалять файлы в `hooks/`, включая `TRIGGERS.md`, можно только по прямой просьбе пользователя.
- Новый хук — по шаблону `templates/hook.md`. После создания, переименования или удаления хука обнови таблицу «Список хуков» в `hooks/README.md` и строки этого хука в `hooks/TRIGGERS.md`.

## Сводка

`$ROOT` — папка этого файла; пути машины задаются в `env.yaml`, проект — в `workspaces/<ws>/ws.yaml`, задача — в `workspaces/<ws>/tasks/<задача>/task.yaml` плюс файл описания. Права на правки даёт `access` источников в `ws.yaml`; правки идут только в worktree задачи на ветке из `task.yaml`. Перед работой читаются `env.yaml`, `rules/`, `ws.yaml`, правила пространства, `task.yaml`, описание и правила репозитория. Все YAML проверяются по схемам из `rules/config.md`; если что-то не сходится — агент останавливается и спрашивает. Секреты берутся из `$SECRETS` по ключам из `ws.yaml` и никуда не выводятся. Хуки запускаются по `hook:<имя>` или по событиям из `hooks/TRIGGERS.md`.
